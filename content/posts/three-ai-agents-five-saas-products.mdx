I gave the same prompt to three autonomous coding agents (Droid, Claude Code, and Jules) and let each of them loose on a fresh repo. There were no human checkpoints and no clarifying questions. Each agent was to run without pausing and push to main when it was done.

The prompt asked for a real, production-ready SaaS: research the market, pick a novel idea, and build it on Next.js 14+ with TypeScript, Prisma + PostgreSQL, NextAuth, Stripe checkout with webhooks, shadcn/ui, the whole stack. It had to be a real product a real person might pay for, which ruled out toys and CRUD dashboards.

Droid and Claude Code each did one run and shipped one product. Jules did three separate runs in the same repo and shipped three. That makes five products in total.

## The headline numbers

On a seven-dimension scorecard (code quality, problem selection, architecture, monetization, market need, business ceiling, prompt adherence), the overall ranking was:

- Claude Code: 7.6
- Droid: 6.5
- Jules: 4.7 (average across three runs)

Stop there and you have a boring story: "Claude wins, Google loses, news at 11."

## Three failure modes, not one gradient

The ranking puts all three agents on a single scale, as if they made the same mistakes in different amounts. They failed in completely different ways, and I find that more interesting than the ranking.

Droid writes the cleanest TypeScript I've seen from any coding agent. It really does honor strict mode, with no `as any` casts and no disabled lint rules. Its Stripe webhook handles three event types (checkout completion, subscription updated, subscription deleted), which is the most complete subscription lifecycle of the five products. The regulatory research was real too. Droid picked EU Directive 2024/1799 (Right-to-Repair) as its domain, cited the directive correctly, got the July 2026 transposition deadline right, and accurately noted which EU countries had already transposed it as of the build date. You don't get all of that right by pattern-matching.

The catch is how narrow the ambition is. The execution was perfect, but the addressable market is maybe 10,000 manufacturers. The demand is driven by compliance, so it's temporary, and the risk of churn after the deadline is real.

Claude Code did almost the opposite. It picked scope creep in professional services, a universal $12B+ pain point for freelancers, agencies, and consultancies, and built a GPT-4o-powered contract analysis pipeline that classifies logged work against scope and auto-generates change orders. That's a novel category with a massive TAM, and it's the only product of the five with a plausible path to venture-scale growth. It also tied its pricing tiers to AI analysis quotas instead of arbitrary seat counts, which is a smart move: each GPT-4o call has a real inference cost, so the tier limits match the cost structure.

Then I read the code. `session.user as any` appears in nine-plus files across the codebase, systematically overriding the strict TypeScript config that was set up one directory over. The PATCH handler at `api/projects/[projectId]/route.ts` passes the raw request body straight into `prisma.project.updateMany` with no validation. That goes past style into a real vulnerability: an authenticated user can modify arbitrary fields. The main project page is 565 lines in a single component. The strategy was brilliant and the tactics were a mess.

## The Jules pattern

Jules is a different kind of story. It did three runs and shipped three products (InspectLite, RetainerHub, SubCert), with the same failures in every single one:

- SQLite instead of PostgreSQL, every time.
- Zero Stripe webhooks across all three products.
- ESLint's `no-explicit-any` and `react-hooks/exhaustive-deps` disabled instead of satisfied, in two of three.
- The stock `create-next-app` README left in the repo, in two of three.
- `.env` files committed to git, in two of three (the `.gitignore` only excluded `.env*.local`, so `.env` itself went in).

Then there were the specific ones that got me.

SubCert's sign-up flow writes `password: "hashed_password_mock"` directly into the database. There's a code comment that says "skip real hashing for pure mock." `bcryptjs` is installed and listed in `package.json`, but nothing imports it. This shipped as "production-ready."

InspectLite has an "Add Item" button with no `onClick` handler. It just sits there.

RetainerHub's nav links to `/dashboard/clients`, which returns a 404 because the route was never built (only `/dashboard/clients/[id]` exists).

And all three are basic CRUD apps, which the prompt explicitly forbade.

The individual failures interest me less than the fact that the same ones repeated across three independent runs. A bad draw doesn't repeat like that, so I read it as a lower internal bar for what "production-ready" means.

## The orthogonal-strengths problem

The two agents that finished well, Droid and Claude Code, have strengths that don't overlap.

Droid has execution discipline. It doesn't cut corners on fundamentals: there's no `any`, no disabled rules, and no mocked systems. Ask it to build something and it will build that thing correctly, within the scope of what you asked for.

Claude Code has judgment. It picked the best problem, framed it as a new category ("we help you recover lost revenue" is the strongest commercial narrative of the five products), and built the most technically ambitious product. It also shipped a security vulnerability and a 565-line monolithic page component.

An agent that picked problems like Claude Code and wrote code like Droid would be formidable. It doesn't exist yet. I also don't think that combination comes automatically: discipline and ambition seem to trade off in current agents, and that might not be purely a coincidence.

## Where all three lost together

None of the five products enforced its own pricing plan limits at the API level. Droid defined `maxProducts` and `maxMembers` per tier and then never checked them anywhere. Claude Code defined AI analysis quotas and never checked them either. A free user can create unlimited records and gets unlimited GPT-4o inference. Even the best agents build monetization that demos well and then breaks the unit economics in production, the second a real user signs up.

None of them produced a formal competitive analysis artifact or used Turbopack, and none fully satisfied the prompt.

## What I took away

The capability gap between the top two and Jules has less to do with raw coding skill than with what each agent considers "done." Jules happily ships mocked auth and calls it production. Droid writes a scoring engine with pure functions and no side effects because that's what the problem calls for. I'd call that a values gap. Training data, scaffolding, system prompts, whatever: something gives these agents different internal definitions of "finished," and that difference shows up everywhere.

Autonomy amplifies that difference. If you hover over an agent diff by diff, you catch the shortcuts. Walk away and let it push to main, and you find out what it thinks "finished" means. The gap between Jules and Droid narrows when you're reviewing every change and widens a lot when you're not.

Three outputs aren't better than one good one. Jules shipped three products against one each from Droid and Claude Code, and it scored lowest on every dimension. The quantity didn't make up for anything. If throughput is your eval for coding agents, you're measuring the wrong thing.

The security finding has stuck with me. ScopeShield was the highest-scoring product overall, and it had an authenticated-user-can-modify-arbitrary-fields bug that nobody would catch without reading the route handler. That kind of bug passes most code reviews, because most code reviews don't read API routes line by line looking for Prisma writes that trust the request body. It's also the kind of bug my team and I are building Infiniview to catch. I didn't run the experiment to validate my own product, but it did that anyway.

## Where this leaves me

More optimistic than I expected. The top agents are not that far off from being trustworthy for greenfield work, as long as someone reads the diff. The gap between "impressive demo" and "production" is real but closing. And the failures that remain (security vulnerabilities, unenforced business logic, inconsistent `any` usage, mocked-out systems shipped as real ones) are exactly the kind of thing a review layer should catch.

I ran three agents and got five products with zero humans in the loop, and the clearest lesson is still that someone has to read the code.
